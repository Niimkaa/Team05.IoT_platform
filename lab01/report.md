3. Дүгнэлт
Raspberry Pi 3B+ дээр MQTT broker болон bridge орчныг ажиллуулж, 50, 100, 200 виртуал төхөөрөмжийн нөөцийн хэмжилт хийсэн. Өмнөх 200 төхөөрөмжийн туршилтын интервалд хамгийн багадаа 520 MiB боломжтой RAM үлдсэн, swap-in/out 0, Mosquitto CPU дундаж 4.36%, температур 34.3–36.5°C, throttle 0x0 байсан. Иймээс хэмжсэн нөхцөлд RAM болон CPU ханалтын шинж илрээгүй.

Дахин ажиллуулсан 200 төхөөрөмжийн simulator нийт 24,000 мессежийг 126.9 секундэд илгээж, нийт дундаж хурд 189.2 msg/s гаргасан. 200 холболт амжилттай үүсэж, алдаа бүртгэгдээгүй. Туршилтын төгсгөлийн 200 disconnect нь клиентүүд ажлаа дуусгаад хэвийн салсантай холбоотой.

Cloud талын EMQX, InfluxDB, Grafana, Registry үйлчилгээнүүд нийт 27.24 секундэд бэлэн болсон. Тухайн үеийн дөрвөн контейнерийн RAM нийлбэр 387.57 MiB байсан.

Latency туршилтаар 300 мессежийн аль ч замд алдагдал гараагүй. Гэвч P99 latency Loopback 3.657 ms, LAN 235.535 ms, Bridge 294.922 ms байсан. Bridge нь LAN-аас 1.25 дахин өндөр P99 latency-тай байсан.

Сүлжээний зурвасын өргөн болон брокерын queue/processing хугацааг тусад нь хэмжээгүй тул latency-ийн өсөлтийн шалтгааныг зөвхөн энэ туршилтаар бүрэн ялгах боломжгүй. Мөн simulator-ийн дахин туршилтын үеийн Pi-ийн нөөцийн хэмжилт тусдаа бүртгэгдээгүй тул өмнөх нөөцийн үзүүлэлтүүдтэй нэг туршилтын хэмжилт мэт нэгтгээгүй.

4. Хяналтын асуултын хариулт
1. Гурван замын P99 latency хэд дахин ялгаатай вэ? Гол шалтгаан юу вэ?
Зам	P99 latency
Loopback	3.657 ms
LAN	235.535 ms
Bridge	294.922 ms

- LAN-ийн P99 нь Loopback-аас 64.4 дахин өндөр.
- Bridge-ийн P99 нь Loopback-аас 80.6 дахин өндөр.
- Bridge нь LAN-аас 1.25 дахин өндөр.
Loopback нь сүлжээ ашиглахгүй. LAN болон Bridge замд сүлжээний дамжуулалт, broker боловсруулалт, queue-ийн хүлээлт зэрэг нэмэлт үе шат ордог. Гэхдээ одоогийн хэмжилт эдгээр шалтгааныг тус тусад нь ялгаж хэмжээгүй.

Ялгахын тулд broker-ийн CPU, queue-ийн урт, processing хугацаа болон сүлжээний RTT-г тусад нь хэмжих хэрэгтэй.

\[

Гэвч энэ тооцоонд OS болон бусад процессын хэрэглээ ороогүй. 2 GB RAM нь илүү нөөц өгөх боловч платформын бүх шаардлагыг хангана гэж зөвхөн энэ тооцоогоор батлах боломжгүй. Лабораторийн зааварт дурдсан ThingsBoard-ийн 4 GB хөгжүүлэлт/PoC шаардлагатай харьцуулахад 2 GB хүрэлцэхгүй.
4. cleansession false-ийг true болговол юу өөрчлөгдөх вэ? Ямар үед true зөв вэ?
cleansession false үед MQTT session хадгалагдаж, холболт тасарсан хугацааны subscription болон QoS 1/2 мессежийн төлөв үргэлжлэх боломжтой.

true үед холболт дуусахад session устаж, дараагийн холболт шинэ session эхлүүлнэ.

Өмнөх session болон offline мессежийг хадгалах шаардлагагүй түр зуурын клиентэд true тохиромжтой. Харин offline үед ирсэн мессежүүдийг дараа нь хүлээн авах шаардлагатай тогтвортой төхөөрөмжид false тохиромжтой.
5. Өөр баг SITE=shutis ашиглан нэг broker-т холбогдвол юу болох вэ? Хэрхэн сэргийлэх вэ?
Ижил topic namespace ашиглавал багуудын мессеж нэг сэдвийн орон зайд холилдох, өгөгдөл андуурагдах эрсдэлтэй.

Сэргийлэх хоёр арга:
1. Topic namespace тусгаарлах: Баг бүрд давтагдашгүй prefix өгөх. Жишээ нь cnc302/team05/#, cnc302/team06/#.
2. Broker дээр ACL тохируулах: Баг бүрд тусдаа хэрэглэгч үүсгэж, зөвхөн өөрийн topic namespace-д хандах эрх олгох.
6. vcgencmd get_throttled нь 0x50000 буцаавал юу гэсэн үг вэ? Өмнөх хэмжилтүүд хүчинтэй юу?
0x50000 нь өмнө undervoltage болон throttling тохиолдол бүртгэгдсэнийг илтгэх түүхэн flag-уудыг агуулна.
- 0x10000 — өмнө undervoltage илэрсэн.
- 0x40000 — өмнө throttling болсон.
- 0x50000 — дээрх хоёр түүхэн төлөв хоёулаа бүртгэгдсэн.
Энэ нь заавал яг одоо throttling идэвхтэй байна гэсэн үг биш. Гэхдээ тухайн үйл явдал хэмжилтийн үед болсон бол гүйцэтгэлд нөлөөлсөн байж болно.

Өмнөх хэмжилтүүдийг бүрэн хүчингүй гэж үзэхгүй. Харин тэжээлийн хүчдэлийн нөлөөгүй хэвийн нөхцөлд авсан гэж батлах боломжгүй. Тэжээлийн эх үүсвэрийг шалгаж, тогтвортой болгосны дараа хэмжилтийг дахин хийж баталгаажуулах хэрэгтэй. Манай бүртгэгдсэн туршилтуудад get_throttled=0x0 байсан.
